# 测试工具 · 多角色评审与缺口清单

> 评审对象：NEXUS COCKPIT（诊断网站 + 台架测试台 + 各通道桥接 + 8D 报告）
> 目的：从六个角色视角找出「还缺什么」，并给出优先级与落地顺序。

---

## 一、现状盘点（已具备）

| 能力 | 状态 |
| --- | --- |
| 三域诊断视图（CDC/MDC/VDC，12 类模块） | ✅ 有 |
| 日志解析 → 事件时间轴 → 8D 报告（HTML/PPT） | ✅ 有 |
| 台架外设自检（8 类） | ✅ 有（部分为模拟） |
| 老化 / 温循用例循环（7 个用例） | ✅ 有 |
| CAN 收发（周立功，含模拟） | ✅ 有（TCP 待实机） |
| 单机、纯前端 + 本地桥接 | ✅ 有 |

**本质**：目前是一个「单机、单人、临时会话」的调试工具。要变成「团队可用、可交付」的产品，缺的是**工程化外壳**。

---

## 二、六个角色分别在意什么

### 1. 产品经理

| 关注 | 现状 | 缺口 |
| --- | --- | --- |
| 定位与用户 | 面向自己/团队 | 没区分角色：研发调试 vs 产线检测 vs 售后诊断，需求不同 |
| 价值度量 | 无 | 缺指标：定位故障耗时、一次通过率、8D 产出量 |
| 版本节奏 | 手工 | 无版本号/变更日志/灰度 |
| 商业模式 | 自用 | 若对外：单机授权？按台架？云端订阅？ |
| 交付形态 | 网页 | 客户要的是「一个装好就能用的包」，不是源码 |

**建议**：先明确一句话定位（例：*面向座舱 DV 阶段的台架诊断与老化执行工具*），再按角色拆三个入口：**调试 / 台架 / 老化**。

### 2. 测试经理

| 关注 | 现状 | 缺口 |
| --- | --- | --- |
| 用例管理 | Excel 68 条 + 页面 7 个自动化用例 | 两套体系没打通：Excel 用例无法驱动执行 |
| 追溯矩阵 | 无 | 需求 ↔ 用例 ↔ 结果 ↔ 缺陷 的链路缺失 |
| 回归策略 | 手工点 | 缺「冒烟 / 全量 / 老化」三档套件与一键回归 |
| 缺陷闭环 | 有缺陷模板 | 未接 Jira/禅道，状态不同步 |
| 覆盖率 | 有模块矩阵 | 缺指标：模块×用例×结果的热力图 |
| 报告 | 8D + CSV | 缺测试报告（通过率、失败分布、趋势） |

**建议**：把 Excel 用例升级为 **YAML/JSON 用例（步骤+判据+脚本钩子）**，页面读同一份文件执行，测试经理只维护这一份。

### 3. 硬件 SE

| 关注 | 现状 | 缺口 |
| --- | --- | --- |
| 台架拓扑 | 文档有 | 缺「接线自检」：电源、地、终端电阻、线序是否符合拓扑 |
| 电源 | 无 | 缺程控电源控制（拉偏 9–16V、掉电、浪涌） |
| 信号质量 | 无 | 缺 CAN 眼图/终端电阻测量、以太链路误码 |
| 校准 | 无 | 综测仪/音频/温箱的校准状态与有效期未记录 |
| 接触可靠性 | 无 | 缺「插拔 N 次后是否仍通过」的机械耐久记录 |
| 故障注入 | 无 | 缺硬件级注入：短路、断路、误码、时钟抖动 |

**建议**：加一个「台架拓扑图 + 接线自检」页面，把电源/线束/终端电阻做成可勾选的检查项，结果进报告。

### 4. 软件 SE

| 关注 | 现状 | 缺口 |
| --- | --- | --- |
| 架构 | 页面 + 本地桥（SSE） | 无统一后端：多页面各自起桥，端口/状态分散 |
| 数据持久化 | 无 | **刷新即丢**：无时序库、无历史对比 |
| 通道抽象 | 部分统一 | 各桥实现重复（can/bench 两套 SSE 服务器） |
| 协议适配 | 硬编码 | DBC/ARXML、AT 指令表、MCU 命令表都未配置化 |
| 时间同步 | 各通道独立时间戳 | 跨通道事件无法严格排序（缺 PTP/统一时基） |
| 回放 | 无 | 无法用历史数据复现问题 |
| 性能 | 未测 | 24h 老化页面常开，内存/渲染未验证 |
| 安全 | 无 | 刷机/NV 写无权限、无审计、无二次确认 |

**建议**：把两个桥合并成**一个 bench-agent**（单端口、多通道、统一事件总线），并落 SQLite 时序表——这是后面所有功能的地基。

### 5. 客户 / 产线

| 关注 | 现状 | 缺口 |
| --- | --- | --- |
| 上手成本 | 需要跑 Python 脚本 | 客户不会装 Python；需要一键安装包/绿色版 |
| 权限 | 无 | 操作员只能跑检测，工程师才能刷机/写 NV |
| 多语言 | 中文 | 外资客户需要英文 |
| 报告 | HTML/PPT/CSV | 缺客户格式模板（含签名、二维码追溯） |
| 追溯 | 无 | 每台样机的 SN、固件、测试记录未绑定 |
| 售后 | 无 | 出问题要能「一键打包现场证据」发回 |

**建议**：加「样机档案」：SN + 固件版本 + 每次测试记录，导出时自动带二维码，扫码可回溯。

### 6. 质量 / 合规（补充角色）

| 关注 | 缺口 |
| --- | --- |
| 过程证据 | 谁在何时执行了什么、结果如何，需不可篡改的审计日志 |
| 数据安全 | VIN、日志可能含敏感信息，需脱敏与访问控制 |
| 标准对齐 | 若用于功能安全相关验证，需说明工具置信度（不替代 HIL） |
| 环境记录 | 老化必须记录温箱实际曲线，而非只记设定值 |

## 三、缺口清单（按优先级）

### P0 · 不做就没法交付

| # | 缺口 | 说明 | 估算 |
| --- | --- | --- | --- |
| 1 | **统一 bench-agent** | 合并 can/bench 两个桥，单端口多通道，统一事件总线 | 3–5 天 |
| 2 | **数据持久化** | SQLite 存会话/事件/测量，支持历史查询与回放 | 3 天 |
| 3 | **用例配置化** | YAML 定义步骤/判据/钩子，页面读同一份 | 3 天 |
| 4 | **一键安装包** | 免 Python 环境（PyInstaller 打包 agent + 静态站点） | 2 天 |
| 5 | **权限与审计** | 操作员/工程师两级；刷机、NV 写强制二次确认并留痕 | 2 天 |
| 6 | **样机档案 + 追溯** | SN/固件/记录绑定，报告带二维码 | 2 天 |

## 四、三个最值得先做的事（如果只做三件）

1. **统一 bench-agent + 持久化**：现在两个桥、数据不落盘，后面每个功能都要重做一遍；
2. **用例配置化**：把 Excel 的 68 条和页面的 7 个用例统一成一份 YAML，测试经理才愿意用；
3. **一键安装包 + 权限审计**：决定这东西是「自己用的脚本」还是「别人能用的产品」。

---

## 五、一句话总结

现在这套东西的**技术骨架已经对了**（通道抽象、事件模型、8D 闭环），
缺的是**产品外壳**（安装、权限、持久化、报告、多语言）和**测试管理闭环**（用例配置化、追溯、缺陷对接）。

前者决定客户能不能用，后者决定测试团队愿不愿意用。
