为 15–25 万级新能源车
做一套「看得见、听得清、连得上」的座舱

不是堆屏幕，而是用一颗主流 SoC + 虚拟化，把仪表、中控、副驾、HUD 和语音连成一个整体； 硬件按平台化设计，一套域控覆盖三个配置档，摊薄成本。

一句话定位

「20 万级车里最跟手的座舱」——以交互延迟和语音唤醒作为差异化，而不是以屏幕数量。

不做什么
  • 不自研 SoC，用高通/芯驰成熟平台
  • 不做 L3 自动驾驶（那是 MDC 的事）
  • 不追求 8K 屏，优先保证帧率与触控延迟

目标用户

25–40 岁家庭首购/换购；每天通勤 40min；对「车机卡不卡、语音听不听得懂」最敏感。

家庭通勤科技敏感

核心卖点

  • 触控响应 ≤ 100ms，滑动无掉帧
  • 语音唤醒 ≤ 500ms，可见即可说
  • 导航/音乐/电话三任务并行不卡
  • 倒车影像 2.5s 内出图

软件架构

虚拟化双系统：仪表跑 QNX 保实时，中控跑 Android 保生态；中间件统一 SOME/IP 与 Android HAL。

应用层导航 · 音乐 · 语音助手 · 车控 · 视频 · 应用商店
框架层Android Automotive（CarService / Vehicle HAL）· QNX 仪表 HMI
中间件SOME/IP · DDS · CommonAPI · 以太网关 · OTA 客户端
系统层Hypervisor（QNX Hypervisor / 黑莓 IVY）· Linux 内核 · RTOS（安全岛）
硬件层SoC · MCU · SerDes · A2B · 连接模组

为什么用虚拟化

仪表要求「上电 2s 出图、绝不卡死」，Android 启动要 20s+。用 Hypervisor 把两者隔离：仪表跑 RTOS/QNX 独立启动，Android 崩了仪表还在。

关键设计

  • 仪表与中控共享 GPU，按优先级分配
  • 倒车影像走独立通路，绕开 Android 启动
  • 语音常驻低功耗核，唤醒 ≤500ms
  • OTA 双分区 A/B，失败自动回滚

安全与诊断

  • 安全岛监控 SoC 心跳，异常降级
  • 关键信号 E2E 保护（ASIL-B）
  • 预留 UDS / DoIP 诊断通道
  • 日志分级落盘，支持远程抓取

与诊断台架的关系

产品定义里每一条「可验收指标」，都要在 DV 阶段被台架测出来：

  • 冷启动 ≤25s → 台架 ADB 打点 + 计时
  • 倒车影像 ≤2.5s → NGX 抓帧计时
  • 连续 72h 崩溃 0 → 老化循环
  • 触摸 ≤100ms → 高速相机或日志打点

台架不是为了测而测，是把产品指标变成可重复的数字。
