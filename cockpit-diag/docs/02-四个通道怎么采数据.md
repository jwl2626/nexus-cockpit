# 四个通道怎么采数据

你的座舱诊断要发四类指令：**ADB / Fastboot / 周立功 CAN / 以太网**。
这一篇讲每个通道「采什么、怎么判断好坏、坑在哪」，最后给一张**待填空的命令清单表**——
你把具体指令填进去，我就照着接进 `checks/cockpit.json`。

---

## 0. 一次采集的时序（很重要，先定这个）

同一台机器，不同时间点采到的结果不一样。上电 5 秒和上电 60 秒，ADB 的答案可能完全相反。

建议固定一个**采集剧本**，所有机器一模一样地跑：

| 阶段 | 时刻 | 采什么 | 为什么 |
| --- | --- | --- | --- |
| T0 | 上电瞬间 | fastboot 变量、CAN 首帧 | 判断 bootloader / 总线是否正常 |
| T1 | 上电后 30s | ADB 能否连上 | 判断启动快不快 |
| T2 | 上电后 90s | 全部 ADB 检查项、CAN 心跳 | 系统稳定后的基线 |
| T3 | 上电后 120s | 以太网 ping / DoIP | 网络服务起来得晚 |

**总时长控制在 2~3 分钟。** 产线节拍通常 3~5 分钟一台，超过就没法用了。

> 这个剧本本身就是一条重要的「特征」：同一个检查项在不同时刻采，
> 结果不同就说明「启动慢」，这往往比「通不通」更能定位问题。

## 1. ADB 通道

### 采什么

| 目的 | 命令 | 好机的样子 |
| --- | --- | --- |
| 设备在不在 | `adb get-state` | 返回 `device` |
| 开完机没有 | `adb shell getprop sys.boot_completed` | `1` |
| 固件版本 | `adb shell getprop ro.build.display.id` | 有值、符合预期版本 |
| 显示服务 | `adb shell dumpsys display` | 含 `Display Devices` |
| 音频服务 | `adb shell dumpsys audio` | 含 `AudioFlinger` |
| 存储 | `adb shell df /data` | 有 `/data` 且剩余空间 > 5% |
| 崩溃 | `adb shell logcat -d -b crash -t 100` | 无 `FATAL EXCEPTION` |
| 关键进程 | `adb shell ps -A \| grep <你的核心服务>` | 进程在 |
| 启动耗时 | `adb shell getprop sys.boot_completed` 轮询计时 | < 45s |

### 坑

1. **`adb devices` 的输出里天然含 "device" 这个词**，所以本工具用 `get-state` 而不是 `devices` 来判断，否则永远为真。
2. **多台设备同时连**：必须带 `-s <serial>`，否则 `adb` 报 `more than one device`。你的产线如果是多工位，这个一定要处理。
3. **`dumpsys` 输出巨大**（几 MB），一定要 `-t` 截断或只 grep 关键行，否则样本文件爆炸、模型也学不到东西。
4. **先 `adb kill-server` 再采**，避免连到上一台的残留连接。

### 这一条特别值钱

```bat
adb shell getprop | findstr /C:"ro.build" /C:"persist" 
```

把关键属性全抓下来存档。以后出现「同一批机器只有部分坏」，用属性差异对比能秒定位是不是物料批次问题。

## 2. Fastboot 通道

### 采什么

| 目的 | 命令 | 说明 |
| --- | --- | --- |
| 机型 | `fastboot getvar product` | 确认不是刷错包 |
| 当前 slot | `fastboot getvar current-slot` | A/B 分区，判断是否回滚过 |
| 解锁状态 | `fastboot getvar unlocked` | 产线应该是 locked |
| 版本 | `fastboot getvar version-baseband` / `version-bootloader` | 与预期比对 |
| 全部变量 | `fastboot getvar all` | 一次性存下来，以后挖特征用 |

### 坑

1. **`getvar` 的返回走的是 stderr**，不是 stdout。很多脚本在这里翻车。
2. **Windows 版 `fastboot` 不支持按 USB 路径选设备**（`-s usb:1-3`）。如果你们是多台无 SN 设备同时连，
   官方 `fastboot.exe` 是选不准的——这正是工作区里那个 `fastboot-hub` 项目要解决的问题。
   接真实产线时，这一步建议直接复用 fbhub 的协议层，而不是调 `fastboot.exe`。
3. **不要用 fastboot 做写操作来「诊断」**。诊断阶段只读。写操作（flash/erase）风险太高，
   要单独走「维修动作」，不要混进采集流程。

## 3. 周立功 CAN 通道

这是四个通道里**信息密度最高**的，也是最容易采错的。

### 硬件与驱动

```text
周立功 USBCAN-II / USBCANFD-200U 等
  └─ 装官方驱动（ZLG 官网，装完设备管理器里出现 USB CAN 设备）
  └─ pip install python-can
  └─ python-can 用 interface="zlgcan" 后端调用 ZLG 的 DLL
```

本项目的 `diag/channels/canbus.py` 已经封装好，`available()` 会告诉你驱动有没有装好。

### 采什么

CAN 诊断的价值分三类，**从易到难**：

#### (1) 总线活不活 —— 最容易做，收益最大

| 检查 | 怎么看 | 好机 |
| --- | --- | --- |
| 有没有帧 | 监听 500ms，收到几帧 | > 0 帧 |
| 心跳在不在 | 特定 ID（如 `0x18FF0102`）周期性出现 | 周期稳定，如 100ms ± 10% |
| 周期抖不抖 | 相邻两帧时间差 | 抖动 < 20% |
| 有没有错误帧 | 错误帧计数 | 0 |
| 总线负载 | 帧数 / 波特率 | < 40% |

#### (2) UDS 诊断有没有回 —— 需要诊断 ID 映射

| 服务 | 请求 | 正常响应 | 说明 |
| --- | --- | --- | --- |
| 会话保持 | `3E 00` | `7E 00` | 最轻量的「你还活着吗」，**建议每次采集都发** |
| 读 VIN | `22 F1 90` | `62 F1 90 <17字节>` | 顺便校验 VIN 合法性 |
| 读故障码 | `19 02 FF` | `59 02 ...` | **直接拿到 DTC，这是最值钱的特征** |
| 读版本 | `22 F1 89` | `62 F1 89 ...` | 软件版本 |
| 清除故障码 | `14 FF FF FF` | `54` | ⚠️ 写操作，诊断阶段别用 |

#### (3) 信号内容对不对 —— 最难，需要 DBC

用 DBC 文件解包，看具体信号值（车速、档位、门状态）。**建议先别做**，
等你把 (1)(2) 跑通、模型能用了，再考虑。

### 坑

1. **波特率必须对**。500k 的线接 250k 的配置，结果是「一帧都收不到」，看起来像硬件坏了。实际上只是配置错了。
   建议：采集前先扫一遍常见波特率（125k/250k/500k），能收到帧的那个就是对的。
2. **终端电阻**：两根 CAN 线之间应该是 60Ω（两个 120Ω 并联）。测出来 120Ω = 少一个终端，30Ω = 多一个。
3. **诊断 ID 映射**：`0x18DA0BF1` 里的 `0B` 是目标地址、`F1` 是 tester 地址。不同项目不一样，
   别照抄，问清你们的总线规范。
4. **CAN FD vs 经典 CAN**：USBCANFD 才支持 FD，经典 CAN 设备上直接报错。确认你们用的是哪种。
5. **别在整车上随便发诊断请求**。某些请求会改变 ECU 状态（比如进编程会话），
   在整车环境下可能触发别的控制器异常。**只发只读类服务。**

## 4. 以太网通道

### 采什么

| 层次 | 检查 | 命令/方法 | 好机 |
| --- | --- | --- | --- |
| 物理/链路 | 网口 up、速率 | `ethtool eth0`（Linux 侧）| 1000Mbps full |
| 三层 | ping 网关 | `ping 192.168.1.1 -n 4` | 丢包 0%，RTT < 5ms |
| 三层 | 丢包率 | 同上，看「丢失 = 0」 | 0% |
| 四层 | DoIP 端口 | UDP 发 `02 01` 到 13400 | 有回包 |
| 四层 | HMI 服务 | TCP 连 8080 | 3s 内握手成功 |
| 应用 | SOME/IP | SD 报文（UDP 30490） | 有 OfferService |

### 坑

1. **网线直连 vs 交换机**：直连有时不自动协商，要手动设 IP。采集前先 `ipconfig` 确认同网段。
2. **DoIP 需要「路由激活」**：只发 `02 01`（车辆识别请求）通常会有回包；但真正的诊断要先做
   `02 05`（路由激活）。**先只做识别请求**，别一上来就激活。
3. **防火墙**：Windows 侧的防火墙可能挡住回包。工位机建议关掉或加白名单。
4. **IP 配置**：座舱的 IP 段各项目不同（192.168.x.x / 10.x.x.x），采集前要能自动探测，
   别写死——建议加一条「扫描本网段存活主机」的预检查。

## 5. 每台机器存什么（数据格式）

一次采集 = 一个 JSON 文件，长这样：

```json
{
  "unit_id": "CAR-20261027-001",
  "label": "CAN",
  "meta": {
    "batch": "B12",
    "firmware": "V3.2.1",
    "station": "工位A",
    "taken_at": "2026-10-27T10:30:00",
    "elapsed_s": 142.3,
    "tester": "张工"
  },
  "results": [
    {"check_id": "adb.get_state", "channel": "adb", "status": "ok",
     "value": "device", "duration_ms": 85.2, "detail": ""},
    {"check_id": "can.heartbeat", "channel": "can", "status": "timeout",
     "value": "", "duration_ms": 512.0, "detail": "500ms 内没有收到任何报文"}
  ]
}
```

**注意 `label` 和 `meta` 这两个字段：**

- `label`：人工确认的故障类别。**没有它就不能训练**，只能猜。采的时候就让维修工填。
- `batch` / `firmware`：以后切分数据集、查漂移全靠它。**现在不存，以后追不回来。**

## 7. 采集阶段的三个纪律

1. **先只读，不写。** 诊断阶段绝不 flash / erase / 清故障码。
2. **每台机器都存原始 JSON。** 哪怕当下没用上，以后挖特征全靠它。
3. **采集脚本要能断线重试。** 工位上 USB 掉一次很正常，别让一次抖动毁掉整台机的数据。
