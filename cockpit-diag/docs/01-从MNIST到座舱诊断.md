# 从「手写数字识别」到「座舱智能诊断」

你之前做的 MNIST 是：**一张图 → 一个模型 → 一个数字**。
你现在想做的是：**一台车机的诊断记录 → 一个模型 → 一类故障 + 为什么 + 下一步查什么**。

骨架是同一件事。但有三处必须换脑子，否则一定踩坑。这篇文档就讲这三处，以及一条能落地的训练路线。

---

## 一、先纠正一个前提：你不需要「手搓大模型」

你说想「手搓一下大模型」。这句话要先拆开，因为**大模型（LLM）和你这个需求，是两件不同的事**。

| | 训练大模型 | 你真正要的 |
| --- | --- | --- |
| 数据量 | 万亿 token | 几百~几千条诊断记录 |
| 算力 | 上千张 GPU，几个月 | 一台笔记本，几分钟 |
| 输出 | 会说话 | 判得准、说得清、能复现 |
| 谁在做 | OpenAI / DeepSeek 这类公司 | 你自己，这周就能做出来 |

如果你真去「训练一个大模型」，结果会是：数据不够 → 学不会 → 训出来还不如规则。

**但你也没必要放弃 AI。** 正确姿势是把 AI 分成三层用，每层解决不同问题：

| 层次 | 干什么 | 用什么 | 你需要投入 |
| --- | --- | --- | --- |
| **L1 规则** | 「铁证」判定：CAN 一帧都没有 = 肯定不正常 | if-else + 阈值 | 半天，把老师傅的经验写成 JSON |
| **L2 小模型** | 「整体像不像」：13 个检查项的组合模式，人眼看不过来 | 逻辑回归 / 随机森林 | 一天，`python -m diag.cli train` |
| **L3 大模型** | 「为什么、下一步查什么」：把结构化结果翻译成人话，跟你对话 | DeepSeek / 通义 API，**不训练，只调用** | 一小时，接个 API |

**你真正要「训练」的，是 L2。** L3 不用训练，用 prompt + 工具调用就行——那才是「把现有工具告诉 AI」的正确做法。

## 二、从 MNIST 迁移：哪些能照搬，哪些不能

这是最有用的对照表，建议截图存着。

| MNIST | 你的座舱诊断 | 能不能照搬 |
| --- | --- | --- |
| 28×28 灰度图 | 13 个检查项 × 5 种结局 + 耗时 | ❌ 要自己设计「特征」 |
| 60000 张标注图 | 历史维修记录，每类几十条起 | ❌ 你的数据少 2~3 个数量级 |
| 0~9 十个类别，每类均匀 | 6 类故障，不良率 2%~10% | ❌ 严重不平衡，必须加权 |
| 像素值 0~255，稠密连续 | 状态是「成功/失败/超时/报错」 | ❌ 要 one-hot 编码 |
| 用 CNN 提特征 | **不需要**，特征是人设计的 | ❌ 样本太少，CNN 一定过拟合 |
| 随机划分训练/测试集 | **必须按批次/日期划分** | ❌ 随机划分 = 数据泄漏 |
| 看 accuracy | 还要看**漏检率** | ❌ 只看 accuracy 会被坑死 |
| 模型部署到网页 | 部署到产线工位，要能追责 | ⚠️ 要加日志和版本管理 |

三个最容易致命的差异，展开说：

### 差异 1：你的输入不是「天生就是数字」

MNIST 省掉了整个「特征工程」，因为像素天然是数字。你没有这个便宜。

你要自己回答：**「一次诊断记录，怎么变成一串数字？」**

这个项目里的答案是（见 `diag/features.py`）：

```text
每个检查项 × 5 种结局 -> one-hot      13 × 5 = 65 维
全局各结局的比例                       5 维
每个通道的平均耗时、失败率             4 × 2 = 8 维
                                  合计 78 维
```

**为什么要把「超时」和「失败」分开？**
因为耗时 200ms 的 fail 是「业务失败」，耗时 5000ms 的 timeout 往往是「链路卡死」。
同样是 fail，含义完全不同。这是人设计特征时才能加进去的先验，CNN 不会替你想到。

### 差异 2：类别不平衡，accuracy 会骗你

假设不良率 5%，你写一行 `return "OK"`，准确率 95%。看起来很棒，实际一条坏机都没抓到。

所以这个项目里强制报三个数：

| 指标 | 含义 | 代价 |
| --- | --- | --- |
| 准确率 | 整体对多少 | 只用于横向比较 |
| **漏检率** | 坏机被判成好机 | **最贵**：坏机流到客户手里 |
| 误报率 | 好机被判成坏机 | 次要：多拆一台、产线抱怨 |

你刚才跑出来的 demo（默认参数）是：准确率 86.0%，**漏检率 6.7%**，误报率 16.4%。
这就是真实世界的起点，不是 99%。**别信任何 demo 里的 99%。**

### 差异 3：数据泄漏，能让你的模型「假得很漂亮」

最经典的坑：你把 1000 条记录**随机**分成训练集和测试集，准确率 98%。
上线后掉到 60%。为什么？因为里面有 200 条是同一台机器重复测的，模型「背答案」了。

**正确做法：按批次、按日期、按设备切分。**
这个项目里是 `_split_by_batch()`：B00~B09 训练，B10~B11 测试。

真实场景里你还应该保证：**测试集里的固件版本和批次，训练集里没见过。**

## 三、训练到底在训练什么（用你刚跑的结果讲）

你刚才跑的那次训练，屏幕上出现了这些：

```text
epoch    1/200  loss=0.3669
epoch   33/200  loss=0.2273
epoch   66/200  loss=0.2208
...
```

**loss 就是「模型有多离谱」**。它从 0.37 掉到 0.22，表示模型在训练集上越来越准。

然后混淆矩阵：

```text
真实\预测        AUDIO      CAN  DISPLAY      ETH       OK      SYS
AUDIO           20        0        2        0        2        0
CAN              0       15        0        0        0        0
DISPLAY          1        0       22        0        2        1
ETH              0        0        0       18        1        0
OK               0        3       10        3       92        2
SYS              0        0        0        0        1        5
```

读法：**看行**（真实类别），**看对角线**（对的），**看非对角**（错的）。

- `OK` 那一行有 10 个被判成 DISPLAY、3 个 CAN、3 个 ETH —— 这是**误报**（好机被判坏）
- `DISPLAY` 那一行有 2 个被判成 OK —— 这是**漏检**（坏机被判好），最贵
- 如果 `CAN` 和 `ETH` 大量互相串，说明这两类的特征区分度不够，**要加检查项**，不是调参

**关键认知：模型不是万能的。混淆矩阵里串得厉害的地方，正确的解法通常是「加更好的检查项」，而不是「换更大的模型」。**
这也是为什么你后面把真实指令给我，比调模型重要得多。

## 四、七步训练流程（照着做就行）

```text
1. 定标签     →  故障分类体系（6 类够用了，别一上来 30 类）
2. 采数据     →  每类至少 30 条，正常机至少 200 条
3. 特征化     →  已经帮你写好，改 checks/cockpit.json 就行
4. 切分       →  按批次/日期，绝不随机
5. 训练       →  python -m diag.cli train
6. 评估       →  看混淆矩阵 + 漏检率，不看 accuracy
7. 上线迭代   →  每周复测，监控漂移
```

每一步的具体做法：

### 第 1 步：定标签

**不要**一上来分 30 类。类别越多，每类样本越少，模型越学不会。

建议先分 6 类，跟你产线的真实维修工单对齐：

| 标签 | 含义 | 典型判据 |
| --- | --- | --- |
| `OK` | 正常 | 全部检查通过 |
| `DISPLAY` | 显示/屏幕 | 显示服务异常、花屏、黑屏 |
| `AUDIO` | 音频 | 无声音、杂音、麦克风不通 |
| `CAN` | CAN 总线 | 心跳缺失、UDS 无响应 |
| `ETH` | 以太网 | 不通、丢包、DoIP 无回包 |
| `SYS` | 系统/启动 | 起不来、卡开机、ADB 不通 |

**标签从哪来？** 从维修工单来。工单上「更换屏线后正常」就是 `DISPLAY` 的标签。
没有工单的话，让老师傅对着记录标 200 条——这一步省不了，是所有 AI 的地基。

### 第 2 步：采数据

见 `02-四个通道怎么采数据.md`。核心原则：**一台机器跑一遍全部检查项，存成一个 JSON**。

### 第 3 步：特征化

已经写好了。你要做的只是**把真实指令填进 `checks/cockpit.json`**。

每加一个检查项，特征多 5 维，模型自动会用上。**加检查项比调模型有效 10 倍。**

### 第 4 步：切分

```python
# 错的（随机）
random.shuffle(samples)

# 对的（按批次）
train = [s for s in samples if batch_num(s) < 10]
test  = [s for s in samples if batch_num(s) >= 10]
```

### 第 5 步：训练

```bat
python -m diag.cli train --data data/real-samples.json --out models/diag.npz
```

### 第 6 步：评估

看三个东西，按顺序：

1. **混淆矩阵**：哪两类在互相串？
2. **漏检率**：能不能接受？通常要求 < 5%
3. **误报率**：产线能不能接受？通常 < 15%

串得厉害 → 回去加检查项。漏检高 → 调类别权重或加样本。都不行 → 说明这些故障在现有指令下**根本区分不了**，需要新的采集手段。

### 第 7 步：上线迭代

- 每周抽 20 台复测，看判定和人工是否一致
- 记录每次误判，反馈到标签里重新训练
- **固件版本变了就重训**（数据漂移，后面 03 文档细讲）

## 五、现在这个项目里，你该看哪几个文件

```text
checks/cockpit.json   ← 你以后改得最多的文件：检查项清单
checks/rules.json     ← 老师傅的经验，写成规则
diag/features.py      ← 特征设计（78 维怎么来的）
diag/model.py         ← 手写的 softmax 回归，120 行，能看懂
diag/metrics.py       ← 漏检率/误报率怎么算
diag/diagnose.py      ← 规则 + 模型怎么融合
reports/demo-report.md ← 你刚跑出来的报告
```

先读 `model.py`。它是纯 numpy 手写的，没有黑盒：

```python
grad_logits = ((probs - yb) * wb[:, None]) / denom   # 误差 × 权重
grad_W = xb.T @ grad_logits + self.l2 * self.W_      # 梯度 + 正则
```

就是「预测错了多少 → 按错的方向改参数」，跟你学 MNIST 时的梯度下降是同一个东西，
只是从「一张图 784 维」变成了「一台机 78 维」。

## 六、本周你该做的三件事

按顺序，别跳：

1. **把真实指令填进 `checks/cockpit.json`**（半天）
   先只填 10~15 个检查项。不要贪多，不要一上来就 50 个。

2. **拿 5 台好机 + 5 台坏机，各跑一遍 `probe`**（半天）
   ```bat
   python -m diag.cli probe --unit CAR-001 --label OK --out data/CAR-001.json
   ```
   先验证「采集链路通不通」，别急着训练。

3. **扩到每类 30 条，训第一次真实模型**（1~2 天，取决于坏机好不好找）

跑完这三步，你就有了一个**属于自己的、能说清理由的**诊断模型。
之后再谈接大模型做解释和对话——那是 L3，锦上添花。

## 七、最后一句实话

MNIST 的 99% 是精心设计的问题，目的是让初学者成功。
你的座舱诊断是真实问题：数据脏、标签缺、故障会变。

**第一次训练能到 70%~85% 是正常的，第一次上线会掉 10 个点也是正常的。**
真正决定成败的不是模型多花哨，是：

- 检查项设计得好不好（你的领域知识）
- 标签标得准不准（你的维修记录）
- 有没有持续迭代（你的流程）

模型是这里面最不值钱的部分。这话你现在可能不信，做三个月就信了。
