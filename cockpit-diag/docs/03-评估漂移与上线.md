# 评估、漂移与上线

训出模型只是开始。这一篇讲：**怎么判断它能用了、上线后会怎么坏、以及大模型（L3）到底该放在哪。**

---

## 一、验收标准：什么算「能用了」

别用 accuracy 拍板。用这张表：

| 指标 | 建议门槛 | 不达标怎么办 |
| --- | --- | --- |
| 漏检率（坏→好） | **< 5%** | 调类别权重、补坏机样本、加检查项 |
| 误报率（好→坏） | < 15% | 同上；或加「人工复核」环节 |
| 关键类别召回率 | 每类 > 80% | 看混淆矩阵，串到哪类就补哪类的区分特征 |
| 单机诊断耗时 | < 3 分钟 | 砍检查项或并行跑通道 |
| 结果可复现 | 同一输入同一次运行，结论一致 | 固定随机种子，模型版本化 |

**最重要的不是绝对数值，是「比人工强」。**

上线前先做一次对照实验：拿 50 台机器，让老师傅判一遍、模型判一遍，比一比。
如果模型和老师傅一致率 > 90%，就能用；如果只有 70%，先别上，回去看是哪些样本不一致。

---

## 二、模型会怎么坏（数据漂移）

这是真实项目里 90% 的失败原因，比「模型选错了」严重得多。

| 漂移类型 | 现象 | 例子 | 应对 |
| --- | --- | --- | --- |
| **固件升级** | 突然漏检飙升 | 新固件改了 `dumpsys` 输出格式，`expect_contains` 全不匹配 | 检查项里少用固定字符串，多用结构化判断 |
| **物料批次** | 某类误报集中出现 | 换了屏幕供应商，`adb.display` 的耗时整体变长 | 把 `batch` 存进 meta，按批次监控 |
| **产线变更** | 采集失败率上升 | 换了 USB HUB，USB 枚举变慢 | 监控 `skipped` 比例 |
| **季节/环境** | 温度影响 | 冬天低温启动慢 | 加温度/环境字段 |

### 怎么监控

上线后每周跑一次**「金标准集」**：固定 50 台已人工确认的机器，看模型判定和真值的一致率。
一致率掉了 5 个点 → 该重训了。

这个集合要**冻结**，不能拿去训练。

### 一个反直觉的建议

**宁可让模型「不确定」，也别让它「自信地错」。**

本项目的 `Diagnosis.confidence` 就是干这个的。设一个阈值，比如：

```python
if diag.confidence < 0.55:
    # 不自动判，转人工复核
    return "REVIEW"
```

把 10% 的低置信度样本转人工，比强判要安全得多。产线也能接受——他们本来就要人工抽检。

## 三、规则和模型打架了怎么办

一定会发生。处理原则：

| 情况 | 怎么处理 | 理由 |
| --- | --- | --- |
| 规则命中，模型也同意 | 直接判 | 最可信 |
| 规则命中，模型不同意 | **听规则的** | 规则是「铁证」，比如「CAN 一帧都没有」不可能正常 |
| 规则没命中，模型高置信 | 听模型的，但标记「模型判定」 | 模型发现了规则没覆盖的模式 |
| 两者都弱 | 判 `REVIEW`，转人工 | 证据不足 |

本项目 `diagnose.py` 里用 `alpha=0.35` 做加权融合，就是「规则占 35% 话语权」。
你可以按实际效果调：规则更可靠就调高，模型更准就调低。

**⚠️ 一个必须避免的设计：** 别让规则和模型做同一件事。
规则负责「确定的、可枚举的」；模型负责「组合的、模糊的」。重叠越多，维护越痛苦。

## 四、上线形态

### 最小可用版本（一周能做完）

```text
工位 PC
 ├─ 采集脚本（diag.cli probe）
 ├─ 诊断脚本（diag.cli diagnose → 结果写 SQLite / CSV）
 └─ 一个简单的看板（Excel 也行）
```

输出：每台机器一行——`unit_id / 判定 / 置信度 / 理由 / 时间`。

### 加一步：人工复核闭环

```text
模型判 → 维修工确认/纠正 → 纠正结果回写 label → 下周重训
```

**这一步是整个系统能不能持续变好的关键。** 没有闭环，模型三个月后就废了。

### 别做的事

- ❌ 让 AI 自动执行 `flash` / `erase` / 清故障码 —— 一旦判错就是批量砖机
- ❌ 把模型直接塞进产线 PLC 卡控 —— 先并行跑一个月，看误判率
- ❌ 没有人工兜底就全自动放行

## 五、L3：把「现有工具」告诉 AI（你最初想做的那件事）

你说的「我把我的现有工具告诉 AI，让 AI 去帮我分析故障机」——**这件事叫工具调用（tool calling），
现在就能做，而且不需要训练任何模型。**

### 怎么做

1. 把你已有的能力包装成「函数」，写清楚参数和返回：

```json
{
  "name": "probe_can_heartbeat",
  "description": "监听 CAN 总线 500ms，检查心跳报文 0x18FF0102 是否出现",
  "parameters": {"type": "object", "properties": {
    "channel": {"type": "integer", "description": "CAN 通道号，0 或 1"}
  }}
}
```

2. 把函数清单 + 用户的问题一起发给大模型（DeepSeek / 通义，支持 function calling 的模型）

3. 模型返回「我要调用 probe_can_heartbeat(channel=0)」

4. 你的 Python 去执行，把结果扔回给模型

5. 模型基于结果，给出一段人话诊断：

```text
这台机器的 CAN 总线在 500ms 内没有任何报文，同时 Ethernet 到网关也不通。
两个通道同时失效，最可能的原因是整车电源或线束问题，而不是座舱本身。
建议：先测座舱 12V 供电和地线，再单独验证 CAN 收发器。
```

**这段推理是 L3 的价值，也是规则和 L2 做不到的。** L2 只会说「CAN 90%」，L3 会说「为什么」。

### 关键设计原则

| 原则 | 说明 |
| --- | --- |
| **只暴露只读工具** | `probe_*` 可以给，`flash_*` / `erase_*` 绝对不给 |
| **工具要小而专** | 一个工具干一件事，别做一个 `run_anything(cmd)` |
| **返回值要结构化** | 别把 3MB 日志直接喂给模型，先摘要 |
| **给模型「不确定」的出口** | 允许它回答「证据不足，建议人工」 |
| **记录完整调用链** | 每次调用了什么、返回什么，全部留档，方便追责 |

### 三层怎么配合

```text
        ┌─────────────────────────────┐
        │  L3 大模型：解释 + 对话 + 建议  │  ← 不训练，API 调用
        └──────────────▲──────────────┘
                       │ 结构化结论
        ┌──────────────┴──────────────┐
        │  L2 小模型：分类 + 置信度      │  ← 你训练的，本项目
        └──────────────▲──────────────┘
                       │ 特征向量
        ┌──────────────┴──────────────┐
        │  L1 规则：铁证判定             │  ← JSON 配置
        └──────────────▲──────────────┘
                       │ 检查结果
        ┌──────────────┴──────────────┐
        │  采集层：ADB / Fastboot / CAN / ETH │
        └─────────────────────────────┘
```

**顺序别搞反。** 很多人一上来就接大模型，结果发现大模型拿到的是错的数据，说得越流畅越误导。
先把采集和 L2 做扎实，L3 才有意义。

## 六、迭代节奏（建议）

| 周期 | 做什么 |
| --- | --- |
| 每天 | 采集数据自动落盘，看板更新 |
| 每周 | 跑金标准集，看一致率；收集误判样本 |
| 每两周 | 补样本、重训一次，对比新旧模型 |
| 每季度 | 重审检查项清单，砍掉没用的、加上新发现的 |
| 固件升级时 | **强制**重跑金标准集，必要时重训 |

---

## 七、一句话总结

- **L1 规则** 决定「能不能信」，**L2 模型** 决定「准不准」，**L3 大模型** 决定「好不好用」
- 模型会坏，是常态；有监控和闭环，就能自己长回来
- 别追求一次做对，追求**每次上线都比上次好一点**
